# TUG//LAB — TRON Timed Up and Go Biomechanics Lab

A standalone, static, vanilla **HTML/CSS/JS** web app that times the CDC STEADI
**Timed Up and Go (TUG)** test from a phone camera, detects every phase
automatically, computes a full on-device biomechanical / gait analysis, and can
stream pseudonymous results live to Google Sheets. All video and pose processing
happens **on the device** — video never leaves the phone.

> **Not a medical device.** This is a research / screening instrument. TUG is one
> component of fall-risk assessment (CDC STEADI). Results are a screening estimate
> from camera analysis, not a diagnosis.

**This build follows two defining decisions:**
1. **No installation of anything** — no Node, npm, bundler, Git, or Python at any
   step. Classic `<script>` files; MediaPipe loads from a pinned CDN; tests run in
   a browser page; the data dictionary is generated by a browser page; you deploy
   through the GitHub web UI; cloud capture uses Google Apps Script.
2. **Operator-following, portrait camera** — instead of a fixed landscape camera
   framing the whole course, the operator holds the phone in portrait and pans to
   follow the participant (stand → walk to cone → turn → walk back → sit). See
   §6–§7 for how the analysis stays valid with a moving camera.

## 1. Quick start

### Use it (no install)
1. Open the deployed URL on a phone over **HTTPS** (camera needs a secure
   context — `file://` will not work for the camera).
2. Pick an instruction-video language, watch the clip, fill in the participant
   form, tick the pre-test checks, tap **PROCEED**.
3. Set up the camera (grant permission), let the pre-flight checks go green, tap
   **START TEST**. Follow the participant with the phone through the whole trial.
4. The app auto-finishes when the participant is seated and still, analyses the
   recording, and shows results. **Download ZIP** and/or **Submit** (upload).

### Develop without installing anything
| Need | How |
|---|---|
| Get this source | GitHub repo page → **Code → Download ZIP** in the browser; unzip. |
| Edit code | Edit files in the browser (GitHub pencil) or any text editor. |
| Run the tests | Open `tests/index.html` from the deployed site (shows a pass/fail table). |
| Build the data dictionary | Open `tools/build-dictionary.html`, click **Download**. |
| Mobile console | Add `?debug=1` to the URL to load an on-page console + FPS overlay. |
| Analyse without live camera | Entry screen → **Advanced → analyse a video file** (replay), or `?dev=1`. |
| Cloud capture | Google Apps Script (runs in the browser; nothing to install). See §3. |

## 2. Deploying to GitHub Pages via web upload

1. Create a new **public** repo (e.g. `icare-tug`).
2. **Add file → Upload files** and drag in everything at the repo root:
   `index.html`, `css/`, `js/`, `apps-script/`, `tests/`, `tools/`, `docs/`,
   `README.md`, `DATA_DICTIONARY.md`, `.nojekyll`. Keep `index.html` at the root.
3. **Settings → Pages → Source: Deploy from a branch → `main` / `(root)`**.
4. Live at `https://<user>.github.io/<repo>/` after ~1 minute.
5. **Update:** open a file on GitHub → pencil → paste → commit, or re-upload.
   Hard-refresh the phone after each deploy. The running build version is shown
   in the footer; local `<script>`/`<link>` URLs carry `?v=` cache-busting — bump
   them on each release.
6. For iterating without breaking production, use a separate `-staging` repo or a
   `/dev` folder.

## 3. Google Sheets integration (step by step)

1. Create a Google Sheet named **"TUG Lab Data"**.
2. **Extensions → Apps Script.** Delete the default code and paste the contents of
   `apps-script/Code.gs`.
3. **Deploy → New deployment → type: Web app.** Set **Execute as: Me** and
   **Who has access: Anyone**. Authorize when prompted.
4. Copy the Web app **`/exec`** URL.
5. Edit `js/config.js` (GitHub pencil → commit): set
   `CONFIG.sheets.webhookUrl = '<your /exec URL>'`. Optionally set
   `CONFIG.sheets.uploadFrames = true` to also upload the 30 Hz Frames table.
6. **Verify:** open the `/exec` URL in a browser — it should return
   `{"status":"active","service":"tug-lab","schema":"1.0"}`. Or use **Test
   connection** on the History screen in the app.
7. Whenever you change `Code.gs`, deploy a **New version** (Deploy → Manage
   deployments → edit → New version).

The app sends a single `POST` with `Content-Type: text/plain` (no CORS preflight)
containing `{summary, steps, events, frames?}`. The receiver matches columns by
name, appends unknown columns, ignores a `session_id` already present (returns
`duplicate`), and prefixes string cells starting with `= + - @` to block formula
injection. Only pseudonymous numeric data is sent — **never** video, raw
landmarks, or names.

### Troubleshooting
| Symptom | Fix |
|---|---|
| `/exec` GET shows nothing / error | Re-check deployment is a **Web app**, access **Anyone**, and you deployed a version. |
| Upload shows "sent (unconfirmed)" | The browser used a no-CORS fallback; data was sent but the response can't be read. Check the Sheet. |
| Nothing appears in the Sheet | Confirm the webhook URL in `config.js` matches the latest deployment; retry from History. |
| Rows duplicated | They won't be — a repeat `session_id` is ignored by design. |

## 5. Scientific manual — the TUG test
The Timed Up and Go measures basic functional mobility: from seated, the
participant stands, walks 3 m at a normal pace, turns, walks back, and sits. The
time taken is the primary outcome. The CDC STEADI programme uses a cut-point of
**≥ 12 s = at risk for falling**. Originally described by Podsiadlo & Richardson
(1991); widely studied since (Barry et al. 2014 meta-analysis; Bohannon 2006
reference values). It is a screening tool — a slow time flags the need for fuller
assessment, not a diagnosis. Content rephrased for compliance; see §13 for primary
sources.

Interpretation (descriptive bands, Podsiadlo & Richardson as summarised by
clinical sources — verify before publishing): `< 10 s` freely mobile; `10–19.99 s`
mostly independent; `20–29.99 s` variable mobility; `≥ 30 s` impaired mobility.

Limitations: TUG reflects many systems at once (strength, balance, gait, cognition)
and does not localise a cause. A single camera gives 2-D sagittal estimates, not
lab-grade 3-D kinematics.

## 6. Biomechanics of the TUG
The app decomposes the trial into phases and reports mechanics for each:
- **Sit-to-stand:** hip rise, ascent time/velocity, knee & hip ROM, peak trunk lean.
- **Gait initiation & steady gait:** heel strikes / toe-offs (Zeni 2008), stride
  and step length/time, cadence, symmetry, variability, joint kinematics.
- **Turning:** torso yaw change (~180°), peak/mean yaw rate, step count, a
  smoothness proxy (yaw-rate peaks).
- **Turn-to-sit / stand-to-sit:** descent time/velocity, a controlled-descent
  index, trunk lean, knee flexion at seat contact.

## 7. CV and signal-processing methods (incl. portrait panning geometry)
- **Pose:** MediaPipe Pose Landmarker (BlazePose GHUM), `lite`/`full`/`heavy`,
  one pose, on-device, GPU with CPU fallback, pinned CDN version. 17 landmarks are
  used and always drawn.
- **Filtering:** channels resampled to 30 Hz; zero-lag 2nd-order Butterworth
  (forward+backward), ~6 Hz body / ~8 Hz feet, reflection padding.
- **Operator-following camera:** a moving camera breaks the classic
  "image x-axis = walking axis" assumption. TUG//LAB therefore derives geometry
  (joint angles, heel-strike timing, stride length, turn yaw) from MediaPipe
  **world landmarks** (metric, pelvis-origin, camera-motion-invariant). Travelled
  **path distance** is reconstructed by integrating the stance foot's
  pelvis-relative motion: a planted foot slides backward relative to the pelvis as
  the body advances, so body velocity ≈ −(stance-foot relative velocity). This
  needs no fixed image reference and works identically out and back.
- **Geometry recommendations:** hold the phone in portrait, keep the whole body
  (head to feet) in frame, pan smoothly, and keep the walk roughly parallel to the
  camera so depth stays stable (the `DEPTH_DRIFT` flag warns otherwise).

## 9. Quality control
Each session carries `qc_flags` and `qc_pass`. **Blocking** flags withhold the
age-norm comparison (the time is still shown, with a warning banner); **warnings**
are informational. Full list and triggers: dictionary §9. The results screen shows
plain-language fix tips for each flag.

## 10. Norms and interpretation
- **CDC cut-point:** ≥ 12 s = at risk.
- **Tiers (UI colouring only, app convention):** low `< 10`, moderate `10–<12`,
  high `≥ 12`.
- **Alternate cut-point:** ≥ 13.5 s flag (Barry 2014).
- **Age norms (Bohannon 2006, verify before publishing):** 60–69: 8.1 (7.1–9.0);
  70–79: 9.2 (8.2–10.2); 80–99: 11.3 (10.0–12.7) s. Shown only for valid completed
  tests with age in band.
- **`fall_probability`** is intentionally empty — the IntelliCARE server ML model
  is not reproduced on-device.

---

## 11. Limitations
Single-camera 2-D estimates; pose model and lighting dependent; a moving camera
reconstructs distance from stance-foot motion (validate distance metrics, see
`docs/VALIDATION.md`). Risk tiers beyond the CDC cut-point are a UI convention. Not
a medical device; not a substitute for clinical assessment.

## 12. Project structure & developer notes
```
index.html              entry; loads css + js in order
css/styles.css          TRON theme, portrait-first, fluid
js/
  config.js             ALL parameters (CONFIG) + webhook + norms + video IDs
  strings.js            UI text (en; zh/yue-ready)
  schema.js             data schema (single source of truth)
  util.js               shared helpers (BMR, stats, storage)
  dsp.js                resample, Butterworth filtfilt, derivative, peaks
  analysis.js           authoritative offline engine (TUGAnalysis.run)
  live.js               causal live state machine
  pose-engine.js        MediaPipe + camera + overlay + replay (ES module)
  export.js             CSV / ZIP / Sheets POST / outbox / history
  charts.js             dependency-free canvas charts
  app.js                router / screen controller
  screen-*.js           entry / setup / live / results / history
apps-script/Code.gs     Google Sheets receiver
tests/                  browser test runner (index.html) + synth + tests
tools/build-dictionary.html   generates DATA_DICTIONARY.md
docs/                   BRIEF.md, VALIDATION.md
```
Tests run in the browser (`tests/index.html`) with zero dependencies. A
consistency check fails if any schema field lacks a description, unit, or
calculation note.
